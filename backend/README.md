# Private weekly respiratory pilot

FastAPI, Python 3.11+, PostgreSQL (psycopg 3). SQLite is for disposable offline testing, not production. This service is independent of the official data pipeline and GitHub Pages. Never put the database, invites, tokens, logs, backups or individual check-ins under `docs/`, in Git, CI artifacts or the static site's JSON. No live service or participant data ships with this project.

## Contract

- `GET /v1/regions` → `{regions:[{code,name,level,parent_code}]}`. Use the catalog, never infer a district from GPS or an IP. National `000000` is a query-only sentinel, not an administrative code. All 31 mainland province-level units; Beijing and Guangzhou have city and district selectors; the catalog intentionally has no nationwide district coverage.
- `POST /v1/enroll` JSON `{"invite_code":"..."}` → `{"token":"..."}` (200). One privately issued 256-bit invite per participant, usable once within 24h. Only domain-separated HMAC-SHA256 digests are stored. Treat the returned bearer as an ongoing capability to edit that participant's retained entries. Never use URL parameters for secrets. Lost token cannot be recovered; prevent duplicate enrollment administratively.
- `GET|PUT|DELETE /v1/checkins/{YYYY-MM-DD}` requires `Authorization: Bearer …`. The date is the Monday of a China-local calendar week (UTC+8). `PUT` JSON `{"region_code":"440106","symptom":"new","observation":"usual","consent":true}`. `new` means onset this week; `ongoing` means continuing symptoms and `none` means no symptoms. The optional nullable observation (`more`, `usual`, `less`) describes perceived nearby respiratory illness separately. It is not a personal diagnosis and never enters the public numerator. No free text, contacts, precise coordinates, names, IDs or symptom details. Client must show purpose, visibility, retention, optional nature and withdrawal choices before each submission. Omitted observation clears the previous one.
- GET/PUT return `{date,region_code,symptom,observation}`. Current-week PUT inserts or replaces **one** record per credential/week even after changing region. An existing retained week can be corrected, not backfilled. DELETE withdraws one retained week (204, idempotent). No public listing or cross-member lookup. 401 invalid bearer; 403 consumed/expired/unknown invite; 404 missing entry; 422 invalid fields, consent or week. API responses have `Cache-Control: no-store`; only the two anonymous GET endpoints allow cross-origin browser reads.
- `GET /v1/reports/latest?region_code=440106` → `{status,requested_region_code,requested_level,region_code,level,week_start,week_end,metrics}`. Only the last completed week, inclusive Monday–Sunday. `available` means the requested unit or nearest eligible ancestor; show returned geography explicitly. `suppressed` means a snapshot exists, but no safe scope is available (`region_code`, `level`, `metrics` null). `unavailable` means disabled/not yet released, all those fields and dates null. Neither implies zero illness. Never display an old week as current. Available metrics have `sample_band` (`30-59`, `60-119`, `120+`), `new_share_band` (10-point percentage bands, inclusive top band `90-100%`), `trend` (`insufficient_baseline`, `no_clear_rise`, `possible_rise`). No district-specific official estimates or exact counts.

## Publication and privacy

`PUBLISH_PILOT=1` is required on both API and worker. Leave unset unless approved for a monitored opt-in pilot. These are descriptive bands among self-selecting credential holders, not prevalence in the population, pathogen attribution, causal evidence, a forecast or personal risk. `possible_rise` is a crude pilot flag without statistical calibration. Do not use as a stand-alone alert. No real-time refresh from raw check-ins.

The denominator is all participants checking in that week (`new + ongoing + none`), and only `new` is the numerator. Require ≥30 distinct credential holders, ≥5 new, ≥5 not-new; national also needs ≥3 provinces with largest ≤60%. Traverse the tree; where released children would expose a small/sensitive parent remainder, suppress their entire subtrees. Weekly bands only; no arbitrary filters, overlapping date ranges, demographic breakdowns or historical-query endpoints. Thresholds limit disclosure; they are **not** differential privacy or immunity against collusion, repeated observations, skew or invite misuse.

Compare only a cohort reporting within the same scope in all four consecutive closed weeks. Require ≥60% of current participants in that cohort, the same sample and cell minima in every matched week, and national dispersion for each matched national week. Flag only if this week's matched share is ≥10 percentage points above each of the three prior weeks. A displayed band's denominator is the full current sample, not the matched cohort. No trend without that baseline.

Retention default: eight Monday-based weeks **including the current one**, configurable 5–26 (`RETENTION_WEEKS`). Reads/edits outside that window are rejected immediately. Weekly maintenance physically deletes expired application rows and snapshots and clears expired invites. The private pseudonymous credential digest persists to authenticate future voluntary submissions. Fixed weekly snapshots contain only released bands, or an empty object. Later correction/deletion changes raw data and can affect future baselines, never reissues an already published week. To retract misleading output, disable pilot publication on API and worker; do not recompute/replace the same week. For shutdown, revoke credentials, destroy tables, encryption keys and backups according to the approved deletion policy.

## Production runbook (Linux, systemd, PostgreSQL)

1. Before collecting data, name a responsible operator; review consent copy, safeguarding of health data, retention/backups, incident handling and applicable privacy law. Start with synthetic fixtures in an isolated staging DB. Do not enable public publication simply to make a dashboard appear populated.
2. Deploy source under `/opt/community`, writable only by the release operator. Create a dedicated non-interactive `community` OS account. Create a venv: `python3 -m venv /opt/community/.venv` and `.venv/bin/pip install -r backend/requirements.txt` from that checkout; pin and audit the resolved versions in the operational deployment. No DSH profile changes required.
3. Provision an encrypted PostgreSQL database, private network and TLS. Restrict firewall/pg_hba and use `sslmode=verify-full` with the trusted CA (or a protected local Unix socket). Use separate DB roles for setup, API, invite issuer and worker. Do not use a superuser. In a dedicated empty database/schema, define protected env files under `/etc/community` (root-owned, mode 0600). Provide `DATABASE_URL=postgresql://...`, `TOKEN_PEPPER` (random, e.g. output of `openssl rand -hex 32` stored in secret manager; same value for API and issuer), `RETENTION_WEEKS=8`, `PUBLISH_PILOT=0`. Worker currently needs a configured pepper to initialize the store but never hashes credentials; use an independent dummy random secret for its role. Do not log these files or include them in shell history.
4. With setup credentials and the configured environment, run `.venv/bin/python -m backend.cli init` from checkout root (idempotent v1 schema). Grant database CONNECT/schema USAGE as appropriate; API needs `SELECT,DELETE` on invites, `SELECT,INSERT` on members, `SELECT,INSERT,UPDATE,DELETE` on entries, `SELECT` on releases. Worker needs `SELECT,DELETE` on entries/invites and `SELECT,INSERT,DELETE` on releases. Issuer needs only `INSERT` on invites. Table owner is not an application role; deny PUBLIC access. Future schema changes need explicit migration and staging restore tests; `init` does not migrate old tables.
5. Install `backend/deploy/community-api.service`, `community-weekly.service`, and `community-weekly.timer` to `/etc/systemd/system/`. Fill `api.env` and `worker.env` as above. `systemctl daemon-reload`, then `systemctl enable --now community-api.service community-weekly.timer`. Timer fires Monday 00:15 Asia/Shanghai and catches up after reboot. Keep timer running **even when publication is disabled**. No task scheduler belongs inside each API worker. Monitor `systemctl list-timers community-weekly.timer` and service failure status, retry failed runs using `systemctl start community-weekly.service`. The job uses one DB transaction, immutable release key and current closed week only; gaps after extended downtime are not backfilled. Until the latest week is actually released the API reports unavailable. A prolonged worker outage delays physical purging; alert and remediate, not just disable the API.
6. Put TLS termination in front of the loopback listener. Allow only required methods/paths and clients for private routes; disable headers/bodies/query strings, access logs, request recordings and APM capture **at every layer**. Disable PostgreSQL bind-parameter and statement logging for application data; verify logs with synthetic errors. Limit body size (e.g. 2 KiB), concurrency, timeouts and rate-limit enrollment/mutations at the edge; no persistent IP tracking. Do not expose debug/docs, PG or a broad CORS proxy. Static hosting may call only the anonymous GETs. Never embed invites, credentials or writable API keys in static clients.
7. The operator runs `.venv/bin/python -m backend.cli invite` from a non-recorded terminal using issuer credentials, and delivers its single output privately, not through public chat or logs. Issue at most once per participant without storing a sensitive identity-to-symptom roster. A compromised capability can be revoked by the database administrator (delete that member row; cascading FK removes retained check-ins). Identify the member only via an authorized secure process; do not request bearer tokens in tickets. Rotating the pepper invalidates all credentials and invites; plan revocation and controlled re-enrollment without duplicate weekly participation.
8. Check `GET /v1/regions`, verify unauthenticated private GET returns 401, verify no release when disabled, and run synthetic enroll/PUT/GET/DELETE plus weekly job in staging. Restrict and encrypt DB storage, WAL, exports and backups, with bounded recovery retention; document backup expiry to participants. Deletions are logical in PG/MVCC and do not instantly erase backups. Test restores offline, apply missed retention and withdrawals before resuming traffic. Keep an incident contact and stop collection/publication if privacy, sampling integrity or access controls are in doubt. Rollback: stop API and timer, deploy prior compatible release without reverting withdrawals, verify schema, restart and run maintenance before opening traffic.

## Tests

From the repository root: `python -m unittest discover -s backend/tests -p test_store.py -v` needs only Python's standard library. In a disposable venv with `pip install -r backend/requirements-test.txt`, run `python -m unittest discover -s backend/tests -v` for the FastAPI HTTP contract as well. All fixtures are generated locally, use disposable SQLite files and require neither Docker nor a remote service. For a real-driver smoke test, point `TEST_POSTGRES_URL` at a **disposable staging** PostgreSQL database with schema-create permission, then run the full suite. It creates and drops its own random schema; it skips if no URL is set. Tests do not validate production roles, TLS, proxy settings or systemd: stage those separately before issuing real invites.
